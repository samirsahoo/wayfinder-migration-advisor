======================================================================
1. PURPOSE
======================================================================

Everyone in IT Engineering already has Claude Code. Most people use it
like a smarter autocomplete: one prompt, one answer, copy and paste.

This session shows how to use it as an engineering system instead,
safely and effectively, across everyday work: development, testing,
debugging, code review, architecture and analysis.

The core message:
  You don't get better results by memorising more commands. You get them
  by knowing which problem you are solving, and choosing the right
  control: focused context, clear checks, the right model, and real
  guardrails.

5. BENEFITS AND KEY TAKE-AWAYS
======================================================================

What attendees will be able to do after the session:

  1. Work in focused sessions
     One task per session; /clear between tasks; /compact when one task
     runs long. Result: sharper, more reliable answers.

  2. Write prompts that work the first time
     Point with @files, state the goal and why, define "done", say what
     not to touch.

  3. Plan before building
     Use plan mode for anything non-trivial. Fixing a plan takes one
     turn; fixing wrong code takes many, plus review time.

  4. Give Claude a check, and ask for evidence
     Tests, build and lint are the pass/fail signal. Ask for the command
     run and its output, not just "done".

  5. Choose the right model and effort
     Sonnet for routine work, Opus where it counts, higher effort only
     when mistakes are costly.

  6. Put each instruction in the right place
     Advice in CLAUDE.md and skills; guarantees in hooks and
     permissions. Short CLAUDE.md (under 200 lines).

  7. Use Claude across the whole lifecycle
     Not only coding: requirements gaps, architecture options and ADRs,
     tests from acceptance criteria, independent code and security
     review, log triage.

  8. Scale safely
     Sub-agents for focused investigations, worktrees for parallel
     edits, /batch only for work that truly splits.

  9. Stay inside bank guardrails
     No secrets or customer data in prompts, deny rules for sensitive
     files, untrusted input treated as data, no unattended production
     changes, and a human always owns the merge.

Benefits for the team and the organisation:

  - Higher quality: plans, tests and independent reviews catch problems
    before they reach a pull request.
  - Faster delivery: less back-and-forth, fewer rewrites, repeatable
    workflows captured as skills.
  - Consistency: shared CLAUDE.md, skills and hooks mean everyone works
    to the same standards.
  - Safety and compliance: enforced controls (permissions, hooks,
    managed settings) instead of reminders; humans stay accountable.
  - Shared language: one mental model and one decision guide for the
    whole team.
